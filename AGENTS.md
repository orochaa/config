# Repository guide for coding agents

This repository manages workstation configuration. Repository work must be
possible without running its setup scripts or depending on the configured
workstation. Use `CONTEXT.md` for the meanings of repository terms.

## Root scripts

- `bootstrap.sh` downloads the main-branch archive to a temporary directory
  and invokes its `install.sh`.
- `install.sh` runs each module's `install.sh` in the listed order.
- `update.sh` runs each module's `update.sh` in the listed order.
- `sync.sh` runs `update.sh`, then stages all changes, commits them, and pushes
  to `origin` when there are changes.

These scripts change the workstation or repository state. Inspect their code
when changing their behavior; do not run them to validate repository edits.

## Module model

A module is a top-level directory that owns a coherent set of workstation
configuration and provides an install/update pair. `install.sh` applies the
module's repository configuration to the workstation. `update.sh` captures
the workstation's configuration back into the repository. Some modules also
install packages or skip work when their target application is unavailable.

The root scripts are the module registries: each module must be called from
both root scripts, in the same order. The current modules are:

- `git/`: `git/install.sh` installs Git if needed, applies `.gitconfig`, and
  may generate SSH keys and configure identity profiles; `git/update.sh`
  captures `~/.gitconfig`.
- `zsh/`: `zsh/install.sh` installs Zsh if needed, applies shell config, and
  clones its plugins; `zsh/update.sh` captures `.zshrc` and `.p10k.zsh`.
- `vscode/`: `vscode/install.sh` applies settings, keybindings, and extensions;
  `vscode/update.sh` captures them.
- `fastfetch/`: `fastfetch/install.sh` ensures Fastfetch is installed and
  applies its config; `fastfetch/update.sh` captures that config.
- `kde/`: `kde/install.sh` applies KDE config files; `kde/update.sh` captures
  the files listed by that script.
- `konsole/`: `konsole/install.sh` applies Konsole profiles and themes;
  `konsole/update.sh` captures them.
- `plasma/`: `plasma/install.sh` applies Plasma config when Plasma is present;
  `plasma/update.sh` captures the supported config files.
- `scripts/`: `scripts/install.sh` copies managed scripts to `~/scripts`;
  `scripts/update.sh` replaces the repository's script config with `~/scripts`.
- `tools/`: `tools/install.sh` installs missing tools from its catalog;
  `tools/update.sh` generates `tools.md` from that catalog.
- `agents/`: `agents/install.sh` copies the managed skills to
  `~/.agents/skills`; `agents/update.sh` copies that directory into this
  module's payload. Treat `agents/` as configuration payload, not as guidance
  for repository conventions.

## Extending modules

When adding configuration for an application or destination already owned by
a module, extend that module. Update its config payload and both scripts so
install applies the repository version and update captures the workstation
version. Keep any file lists or availability checks consistent in both
directions.

Create a module when the configuration has a distinct owner or lifecycle:

1. Add `<module>/config/` for the managed payload.
2. Add `<module>/install.sh` to apply that payload.
3. Add `<module>/update.sh` to capture it back into the payload.
4. Register both scripts in root `install.sh` and `update.sh`, at the same
   position in each list.

## Package installation

Before adding package installation logic, check whether the target package is
already installed and skip its installation when present. Identify all required
dependencies and ensure each is installed before installing the target package;
install missing dependencies first.

Tools use the existing `tools/` module: add entries to
`tools/config/tools.txt` using its command, source, package, and homepage
fields. Add `tools/installers/<package>.sh` only for a `custom` source.
`tools.md` is generated by `tools/update.sh`; change the catalog rather than
editing the generated table directly.
